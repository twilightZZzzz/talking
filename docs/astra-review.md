# Архитектурное ревью «Утренней речи»

**Рекомендация:** оставить Next.js + Supabase, но изменить медиапоток и модель сохранения. Основной сценарий — запись внутри приложения, локальное видео для просмотра, отдельная аудиодорожка в приватном Supabase Storage, два возобновляемых этапа обработки: транскрипция и разбор. Прогресс хранить в Postgres, локальные черновики и очередь изменений — в IndexedDB.

Файлы не менялись. Ограничения платформ проверены по документации, доступной **16 октября 2026 года**. Работа на физических устройствах и реальные вызовы моделей в это ревью не входили.

## 1. Главные выводы

Стек соответствует масштабу: один пользователь, несколько коротких тренировок в день. Отдельный backend, Redis, микросервисы и собственный постоянно работающий worker на старте не нужны.

Однако в плане есть блокирующие предположения:

| Проблема | Последствие | Решение |
|---|---|---|
| WAV 16 кГц, моно, 16 бит на 150 секунд занимает 4,8 МБ | Не проходит через тело Vercel Function | Загружать аудио непосредственно в Storage |
| `decodeAudioData` принят за универсальный извлекатель звука из MOV | Основной сценарий может сломаться на iPhone | Запись внутри приложения; импорт видео — отдельный проверяемый путь |
| Промпт якобы гарантирует сохранение «э» | Недостоверные счётчики и достижения | Проверка на размеченных записях, ручная коррекция, обозначение приблизительности |
| Нет состояния обработки и идемпотентности | Двойная оплата, зависшие дубли, потеря промежуточного результата | Состояния этапов, сохранение транскрипции, журнал попыток |
| В схеме не различены черновик и сохранённый день | Автосохранение может случайно увеличивать серию | Явная фиксация результата дня |
| Тема не сохраняется | На втором устройстве разбирается другая тема | Снимок задания в сессии и каждом дубле |
| Проверка iPhone оставлена последнему этапу | Главный технический риск обнаружится слишком поздно | Ранний HTTPS-деплой и проверка медиасценария |
| Выбранные модели транскрипции уже deprecated | Потребуется скорый переход | Адаптер транскрипции и обязательный план миграции |

**Актуальное изменение:** OpenAI объявила отключение `whisper-1`, `gpt-4o-transcribe`, `gpt-4o-mini-transcribe` и `gpt-4o-transcribe-diarize` **26 февраля 2027 года**. Строить бессрочную архитектуру вокруг Whisper нельзя. [OpenAI: deprecations](https://developers.openai.com/api/docs/deprecations)

## 2. Next.js App Router и разложение legacy

### 2.1. Страницы

| URL | Назначение |

| `/` | Сегодня: существующий ритуал, прогресс, запись и разбор |
| `/history` | История дней и дублей |

| `/auth/confirm` | Завершение выбранного email-сценария входа |

Главную страницу не нужно превращать в многоэкранный мастер: последовательный сценарий прототипа подходит задаче. Дополнительные страницы нужны для истории, восстановления обработки и настроек.

### 2.2. Серверные и клиентские компоненты

**Server Components:**

- layout, метаданные, первоначальная загрузка профиля и истории;
- проверка доступа;
- получение канонического состояния дня;
- подготовка начального снимка для клиентского интерфейса.

**Client Components:**

- весь интерактивный ритуал;
- поля самооценки и переключение режима;
- таймер и звуковые сигналы;
- камера, микрофон, загрузка файла, проигрыватель;
- очередь синхронизации и локальное хранилище;
- обновление карточки разбора.

Это соответствует разделению App Router: браузерные API и интерактивное состояние остаются на клиентской границе. [Next.js: Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)

Не ставить клиентскую границу на корневой layout. При этом дробить каждую подпись и карточку на отдельный серверный компонент тоже не требуется.

### 2.3. Где живёт состояние

Нужны три явно разделённых слоя:

| Слой | Содержание |
|---|---|
| Postgres | Подтверждённые данные, история, результаты анализа |
| IndexedDB | Последний серверный снимок, локальный черновик, ожидающие операции |
| Память страницы | Работа камеры, текущий таймер, проигрывание, открытые панели |

Для ритуала достаточно одного reducer/store на уровне `RitualWorkspace`. Redux для этого масштаба необязателен.

**Автосохранение черновика и «Сохранить день» — разные действия.** Заполненное поле или созданная строка `sessions` ещё не означают завершённую тренировку.

Таймер не синхронизировать между устройствами. На Mac и iPhone это отдельные локальные инструменты.

## 3. Модель данных Supabase

### 3.1. `profiles` / `user_settings` нужна

Рекомендую одну таблицу `profiles`:

| Поле | Назначение |
|---|---|
| `user_id` | PK и FK на пользователя Auth |
| `timezone` | По умолчанию `Asia/Yekaterinburg` |
| `default_mode` | `full` / `exp` |
| `theme` | `system` / `light` / `dark` |
| `created_at`, `updated_at` | Серверные timestamps |
| `revision` | Контроль конкурентных изменений |

Режим по умолчанию относится к профилю, режим конкретного дня — к сессии. Смена настройки не должна переписывать историю.

Тему можно синхронизировать с возможностью локального переопределения на устройстве. Для первого выпуска достаточно общей настройки, по умолчанию `system`.

Триггер создания профиля при регистрации здесь необязателен: владелец создаётся заранее, профиль создаётся вместе с ним.

### 3.2. `sessions`: строка дня, включая черновик

Основной ключ: **уникальность `(user_id, date)`**.

Предлагаемые группы полей:

| Группа | Поля и смысл |
|---|---|
| Идентификация | `id`, `user_id`, `date` типа `date` |
| Контекст дня | `timezone`, `mode`, `content_version`, `rules_version` |
| Задание | `topic_id`, `frame_id`, `challenge_id`, `twister_id`, снимок текста задания |
| Выполнение | `steps_done`, `breath` |
| Черновик разбора | `review_draft`: введённые, но ещё не зафиксированные значения |
| Итог дня | `fillers`, `clarity`, `challenge_done`, `note`, `selected_take_id` |
| Фиксация | `first_saved_at`, `last_saved_at`, `full` |
| Синхронизация | `revision`, `created_at`, `updated_at` |
| Происхождение | `source`, данные импорта/локального времени при необходимости |

**Почему отдельный черновик:** в legacy изменение поля самооценки не меняет сохранённый результат до нажатия кнопки. Синхронизация полей не должна незаметно менять XP и рекорды.

`steps_done int[]` допустим для пяти фиксированных шагов. Нужны уникальные значения и проверка диапазона. Отдельная таблица шагов пока избыточна.

Для новых результатов:

- `fillers` — целое неотрицательное число либо `null`;
- `clarity` — 1–5 либо `null`;
- `challenge_done` — `true`, `false` или `null`;
- `null` означает «не оценено», а не ноль.

`full` имеет особую семантику: в legacy он становится истинным при сохранении полного утреннего ритуала и затем сохраняется. Это исторический факт, его нельзя просто пересчитывать из текущих галочек.

### 3.3. `takes`: дубль и его обработка

Исходную таблицу нужно дополнить:

| Группа | Поля |
|---|---|
| Идентификация | `id`, `session_id`, `user_id`, `take_no` |
| Контекст | Снимок темы, каркаса, челленджа, `previous_take_id` |
| Медиа | `audio_path`, `mime_type`, `size_bytes`, `duration_s`, `audio_sha256` |
| Состояние | `status`, `failed_stage`, `error_code`, `lease_expires_at` |
| Транскрипция | `transcript`, `words`, при необходимости `segments` |
| Анализ | `metrics`, `feedback` |
| Версии | Модели, версия промпта, метрик и схемы результата |
| Время | `recorded_at`, `created_at`, `updated_at`, `analyzed_at` |
| Коррекция | Ручные поправки отдельно от исходного результата модели |

Состояния: `created → uploaded → transcribing → transcribed → analyzing → succeeded`, плюс ошибка конкретного этапа.

`words`, `metrics`, `feedback` в JSONB подходят. Всё, что используется для ключей, ограничений, сортировки и состояния обработки, должно быть обычными колонками.

Номер дубля назначать сервером атомарно. Локальная запись получает UUID сразу; при работе без сети её серверный номер может появиться позже.

**Связь владельцев:** одного FK `session_id` недостаточно при дублировании `user_id`. Нужен составной FK `(session_id, user_id)` на соответствующую пару в `sessions`, чтобы дубль нельзя было привязать к чужому дню.

### 3.4. Дополнительные технические таблицы

- **`analysis_attempts`** — этап, номер попытки, статус, время, provider request ID, usage, стоимость. Нужна для лимитов, расследования сбоев и контроля повторной оплаты.
- **`sync_operations`** — уникальный ID применённой операции, пользователь, результат. Нужна для безопасного повторения запросов после потери ответа. Здесь же можно фиксировать хеш выполненного импорта.

Полноценный event sourcing не нужен. Это небольшой журнал технических операций.

### 3.5. Достижения хранить, условия вычислять

Таблицу `achievements` оставить:

- PK `(user_id, code)`;
- дата открытия;
- точный timestamp, если известен;
- версия правила;
- источник: `calculated` / `legacy`.

Причины хранения:

1. Legacy сохраняет достижения навсегда.
2. После редактирования истории условие может перестать выполняться.
3. Нужна синхронизация между устройствами.
4. Для старых достижений известна дата, но не точный момент.

Проверка условий — чистая функция; выдача — серверная идемпотентная операция. Удалять достижение при обычной правке дня не следует.

Для серий и недельных достижений проверять **всю историю**, а не только текущую серию и текущую неделю, как сейчас делает `checkAch()`.

### 3.6. XP: серверный результат и клиентский предварительный расчёт

Рекомендую:

- факты хранятся в БД;
- общий XP не хранится как вручную увеличиваемый счётчик;
- канонический XP вычисляет сервер;
- клиент использует ту же чистую функцию для мгновенного и офлайн-отображения;
- после синхронизации серверный результат заменяет предварительный.

При нескольких сотнях или тысячах дней полный пересчёт дешёвый. Загружать для него все транскрипты не нужно — достаточно компактных данных дней и успешных анализов.

Пересчёт достижений после записи можно сделать восстанавливаемым: повторять при следующей загрузке, если предыдущий запрос оборвался. Не помещать AI-вызовы в SQL-триггеры.

### 3.7. Индексы, ограничения, RLS

Минимальные индексы:

- `sessions`: unique `(user_id, date)`;
- `sessions`: unique `(id, user_id)` для составного FK;
- `takes`: unique `(session_id, take_no)`;
- `takes`: `(user_id, created_at)`;
- `analysis_attempts`: `(user_id, created_at)`, `(take_id, stage)`;
- `achievements`: PK `(user_id, code)`;
- `sync_operations`: unique `(user_id, operation_id)`.

GIN-индексы на JSONB пока не нужны.

RLS включить на всех доступных через API таблицах. Для чтения проверять владельца; для записи — владельца и допустимый новый `user_id`. У `UPDATE` нужны и проверка исходной строки, и проверка нового состояния. Права на таблицы и RLS — разные уровни защиты. [Supabase: RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

Для этого приложения удобно направить изменения прогресса через серверные endpoints. При этом:

- обычные операции выполнять в контексте проверенного пользователя;
- серверные результаты анализа не разрешать произвольно обновлять из браузера;
- привилегированный клиент держать в отдельном серверном модуле;
- служебные RPC ограничить по правам вызова.

**Важная актуальная деталь:** новые таблицы Supabase могут требовать явных `GRANT` для Data API. Изменение уже применяется к новым проектам, общий rollout указан на 30 октября 2026. Миграция должна явно задавать необходимые права. [Supabase: изменение экспонирования таблиц](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)

Триггер полезен для `updated_at` и увеличения `revision`, если разрешено несколько путей записи. При единственном строго контролируемом пути это можно делать в транзакции без триггера.

## 4. Детерминированный день и геймификация

### 4.1. Определение даты

Тренировочная дата определяется **таймзоной профиля**, а не Mac, iPhone или сервера.

Порядок:

1. Получить календарную дату в `Asia/Yekaterinburg`.
2. Превратить её в целочисленный номер календарного дня относительно фиксированной эпохи.
3. Выбрать контент по этому номеру и версии каталога.

Не использовать UTC-дату из `toISOString()` и не переносить текущую формулу через локальную полночь устройства.

Для Екатеринбурга можно сохранить текущую последовательность тем, проверив новую формулу на наборе дат legacy.

### 4.2. Сохранять задание обязательно

При создании дня фиксировать:

- исходную и выбранную тему;
- каркас;
- челлендж;
- скороговорку;
- версию контента.

«Другая тема» меняет выбранную тему сессии и синхронизируется. При записи дубля создаётся **отдельный неизменяемый снимок задания**.

Иначе смена темы после первой записи изменит смысл уже сохранённого разбора.

Если два устройства офлайн выбрали разные темы, это конфликт поля сессии. Уже записанные дубли сохраняют собственные задания в любом случае.

### 4.3. Переход через полночь

В legacy `now`, `key`, `dayN` вычисляются один раз при открытии страницы. Долго открытая вкладка продолжит писать во вчерашний день.

Нужно:

- проверять дату при возврате приложения на экран;
- пересчитывать её на границе дня;
- уже начатую запись оставлять привязанной к дню начала;
- предложить перейти к новому дню после завершения текущего действия;
- не переносить прошлые сессии при смене таймзоны профиля.

### 4.4. Что действительно делает `calc()`

В [legacy `calc()`](/Users/sergeychukavin/Desktop/Talking/rech-app/legacy/index.html:318):

- каждый выполненный шаг даёт 10 XP;
- сохранённый результат дополнительно даёт 20 XP;
- выполненный челлендж — 25;
- полный ритуал — 30;
- новый рекорд по паразитам — 30;
- сумма умножается на множитель серии и округляется.

При сохранении автоматически отмечается шаг `3`, поэтому он приносит **10 XP за галочку плюс 20 XP за результат**. Это необходимо зафиксировать тестом: подпись интерфейса «+20» не описывает всю фактическую механику.

Новые AI-бонусы предлагаю считать **после множителя**, отдельно:

- +15 за успешно разобранный уникальный дубль;
- +10 один раз за улучшение второго дубля относительно первого;
- повторный HTTP-запрос и повторная генерация того же результата XP не дают.

Для MVP разумно ограничить начисление AI-бонуса первыми двумя разобранными дублями дня. Это продуктовая поправка к плану, а не текущее правило legacy.

**Сравнивать улучшение по паразитам в минуту**, поскольку первый дубль длится 90 секунд, второй — 60. Меньшее абсолютное число само по себе не доказывает улучшение.

«Метроном»: считать по выбранному итоговому дублю каждого из трёх последовательных календарных дней. Иначе можно случайно выбирать любой удачный дубль задним числом.

## 5. Запись, импорт видео и доставка аудио

### 5.1. Почему предложенный `decodeAudioData` рискован

`decodeAudioData` работает с полными данными файла, не с независимыми фрагментами. Успешное воспроизведение видео не гарантирует успешное декодирование этого файла через Web Audio. [MDN: decodeAudioData](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData)

Нужно различать:

- MOV/MP4 — контейнер;
- HEVC/H.264 — видеокодек;
- AAC и другие — аудиокодек.

Для анализа нужен звук, однако браузер ещё должен корректно разобрать контейнер. Ошибка может зависеть от конкретного файла, браузера, версии iOS и ресурсов устройства.

Сообщение «Открой Safari или Chrome» не является надёжным восстановлением. Пользователь уже может находиться в Safari.

**Память:** 150 секунд декодированного stereo Float32 при 48 кГц — около **57,6 МБ** только PCM. Одновременно существуют исходное видео, его `ArrayBuffer`, выходной буфер и WAV. Для длинного 4K-видео это может закончиться перезагрузкой вкладки.

Проверять размер файла нужно до `arrayBuffer()`, длительность — как можно раньше. Длинный файл следует отклонять до полного декодирования.

### 5.2. Ошибка в лимите WAV

Для PCM 16 кГц, mono, 16 бит:

| Длительность | Размер без существенного учёта заголовка |
|---|---:|
| 60 секунд | 1,92 МБ |
| 90 секунд | 2,88 МБ |
| 120 секунд | 3,84 МБ |
| 150 секунд | 4,80 МБ |

Vercel ограничивает тело запроса функции **4,5 МБ**; multipart добавляет накладные расходы. Поэтому лимит 2:30 несовместим с предложенной передачей WAV. [Vercel: Function limits](https://vercel.com/docs/functions/limitations)

Если оставить передачу через функцию, практический лимит — 120 секунд и отдельная проверка байтов. Лучше убрать зависимость от этого лимита через прямую загрузку в Storage.

### 5.3. Сравнение вариантов

| Вариант | Преимущества | Ограничения | Роль |
|---|---|---|---|
| Видео из галереи → `decodeAudioData` | Сохраняет привычный процесс | Контейнеры, память, большие файлы | Дополнительный путь после проверки |
| MediaRecorder: видео и отдельное аудио | Контроль длительности, не нужно читать большой MOV | Разрешения, фон, необходимость испытать параллельную запись | Основной сценарий |
| Только аудиозапись | Самый простой медиапоток | Нет видеопересмотра | Резервный режим |
| Видео в Storage → серверный FFmpeg | Больше контроля над форматами | Загрузка видео, лимиты хранения, дополнительная обработка | Если галерея обязательна |
| FFmpeg WASM в браузере | Обработка локально | Память, загрузка WASM, CPU и батарея | Не рекомендую для MVP на iPhone |

### 5.4. Рекомендуемый основной путь

Один запрос к камере и микрофону:

- фронтальная камера, умеренное разрешение;
- локальная запись видео для просмотра;
- параллельная запись только аудиотрека из того же потока;
- на сервер отправляется только аудио.

MediaRecorder умеет принимать MediaStream и выдавать сжатые файлы; поддержку MIME нужно определять на устройстве. Не зашивать один формат для всех браузеров. [WebKit: MediaRecorder](https://webkit.org/blog/11353/mediarecorder-api/), [MDN: isTypeSupported](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)

**Параллельные recorder’ы необходимо проверить на конкретном iPhone.** Это первая техническая проверка проекта. Если путь нестабилен, резерв — захват аудио через Web Audio/AudioWorklet с ограниченным размером буфера и формированием WAV.

Дополнительные требования:

- обработка запрета разрешений и потери микрофона;
- завершение всех tracks после записи;
- отмена записи;
- ограничение длительности и объёма;
- предупреждение о прерывании записи при уходе в фон;
- проверка смещения аудио относительно видео для перемотки по таймкодам.

`timeslice` не является точным таймером: Safari может приостанавливать камеру/микрофон, а размеры чанков меняются. [MDN: MediaRecorder dataavailable](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event)

### 5.5. Storage вместо тела функции

Рекомендую **приватный Supabase Storage**, поскольку Auth и БД уже там:

1. Сервер создаёт дубль и разрешает загрузку в конкретный путь.
2. Браузер загружает аудио прямо в Storage.
3. В endpoint транскрипции передаётся только ID дубля.
4. Сервер получает объект и отправляет его провайдеру.

Путь принадлежит пользователю и дублю. Клиент не передаёт произвольный внешний URL для скачивания.

Vercel Blob тоже поддерживает клиентскую загрузку, но добавляет вторую систему хранения и авторизации. Для одного пользователя это не даёт достаточного выигрыша. [Vercel Blob SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk)

Storage устраняет лимит входящего тела функции, **но не ограничения OpenAI и не проблему декодирования MOV**.

Предлагаемый срок хранения аудио — 24 часа после успешного разбора, до 7 дней после ошибки. Удаление выполнять сервером, включая очистку брошенных загрузок. Видео по умолчанию остаётся локально.

Supabase Free включает 1 ГБ Storage, максимальный файл 50 МБ, БД 500 МБ; проект может приостанавливаться после недели неактивности. Для короткого временно хранимого аудио этого достаточно. Для архива исходных iPhone-видео — быстро станет тесно. [Supabase: тарифы](https://supabase.com/pricing)

## 6. Транскрипция, паразиты и качество метрик

### 6.1. Выбор модели

| Модель | Word timestamps для нужного сценария | Вывод |
|---|---|---|
| `whisper-1` | Документированы через `verbose_json` и `timestamp_granularities` | Подходит как временный старт |
| `gpt-4o-transcribe` | Аналогичный word-level интерфейс не поддерживается | Не равноценная замена для таймкодов |
| `gpt-4o-mini-transcribe` | Аналогично | Экономия не решает задачу таймкодов |
| `gpt-4o-transcribe-diarize` | Есть разметка говорящих/сегментов; это не word timestamps | Для одного говорящего не нужен |
| `gpt-transcribe` | Текущий guide не обещает эквивалент word timestamps | Кандидат для долгосрочной транскрипции, требует проверки функциональности |

OpenAI по-прежнему указывает `timestamp_granularities` как возможность `whisper-1`; лимит файлов транскрипции — 25 МБ. [OpenAI: File transcription](https://developers.openai.com/api/docs/guides/speech-to-text)

**Рекомендация для ближайшего выпуска:** Whisper через изолированный адаптер, если испытания подтверждают полезность метрик. До февраля 2027 — обязательная замена.

Внутренний контракт должен допускать отсутствие таймкодов. При смене модели доступны варианты:

- новая ASR с необходимой разметкой;
- отдельный forced alignment;
- временный режим без кликабельных слов, с честно отключёнными недоступными метриками.

Forced alignment выравнивает известный текст по аудио; он сам по себе не восстанавливает «э», удалённые транскриптором.

### 6.2. Промпт не гарантирует сохранение паразитов

Фразу из плана «тогда он их сохраняет» нужно заменить на: **«может повысить вероятность сохранения; требуется измерение качества»**.

Примеры паразитов способны менять поведение ASR, но не превращают её в точный детектор дисфлюенций. Возможны пропуски, нормализация повторений и ложные вставки.

Для первого этапа нужен небольшой набор реальных русскоязычных записей Сергея:

- чистая речь;
- протяжные «э»;
- повторения;
- тихая запись;
- паузы и фоновый шум;
- содержательные употребления «типа», «вот», «значит».

Человек размечает фактические события. Измерять отдельно пропуски и ложные срабатывания.

### 6.3. Словарь находит кандидатов

Примеры:

- «Это значит, что…» — не обязательно паразит.
- «Два типа клиентов» — не паразит.
- «Вот пример» — может быть нормальной указательной конструкцией.

Поэтому:

- арифметика и поиск кандидатов выполняются кодом;
- спорные употребления отмечаются отдельно;
- пользователь может исключить ошибочное совпадение;
- исходный результат сохраняется;
- интерфейс говорит «Найдено возможных паразитов», пока точность не доказана.

Для словаря нужны Unicode-нормализация, работа с дефисами, повторными буквами и многословными выражениями. «Как бы» считать одним событием, а не двумя.

### 6.4. Определения метрик

- **Темп:** число слов / длительность выбранного интервала × 60.
- **Паразиты:** абсолютное число и число в минуту.
- **Паузы:** разрывы между словами как приблизительная оценка, с исключением тишины до начала и после окончания речи.
- **Длительность:** реальное медиа, а не выбранная кнопка таймера.

Нужно заранее выбрать, считается ли темп за всю запись или между первым и последним словом. Рекомендую основной показатель за речевой интервал, а полную длительность показывать отдельно.

Пауза больше 0,7 секунды не обязательно полезна: это может быть обдумывание, сбой, шум или ошибка таймкодов. Для более надёжной оценки можно дополнить анализ детектором речевой активности.

120–150 слов/мин — **целевая зона упражнения**, а не универсальная оценка качества речи.

Исторические ручные количества без известной длительности нельзя незаметно смешивать с нормализованными AI-метриками.

## 7. Поток обработки, таймауты и ошибки

### 7.1. Два этапа лучше одного `/api/analyze`

Рекомендуемый поток:

1. Создать дубль со снимком задания.
2. Загрузить аудио в Storage.
3. `POST /api/takes/[id]/transcribe`.
4. Сохранить транскрипцию и метрики.
5. `POST /api/takes/[id]/feedback`.
6. Сохранить валидированный разбор.
7. Предложить результат для итоговой самооценки дня.

Пользователь видит один процесс с этапами. Два endpoint нужны для восстановления и контроля затрат.

Если Anthropic недоступен, транскрипция уже сохранена. Повторять OpenAI-вызов не требуется.

### 7.2. Vercel Hobby

При Fluid Compute максимальная длительность функции Hobby сейчас — **300 секунд**. Это не старое ограничение в 10 секунд. Для этих обработчиков выбрать Node.js и явно зафиксировать нужный `maxDuration`. [Vercel: ограничения функций](https://vercel.com/docs/functions/limitations)

Разделение нужно прежде всего ради надёжности. Два запроса не гарантируют обработку за 20 секунд.

Задать отдельные таймауты провайдеров с запасом до лимита функции: например, до 120 секунд на транскрипцию и 90 секунд на разбор, затем уточнить по измерениям.

### 7.3. Прогресс и закрытие приложения

Для первого выпуска достаточно:

- прогресса загрузки;
- этапов «Распознаём речь», «Готовим разбор»;
- опроса статуса активного дубля;
- восстановления по ID после перезагрузки.

Не показывать выдуманные проценты генерации.

SSE можно добавить для удобства, но он не продлевает срок жизни функции и не обеспечивает гарантированное завершение после закрытия PWA.

**Базовый контракт:** после повторного открытия приложение показывает готовый результат либо предлагает продолжить незавершённый этап. Если требуется гарантированная работа без открытого приложения, понадобится долговечная очередь/workflow; одного `after()` или `waitUntil()` недостаточно.

### 7.4. Идемпотентность

Для каждого этапа:

- один активный исполнитель, захват через атомарное обновление БД;
- ограниченная по времени блокировка;
- уникальность `(take_id, stage, analysis_version)`;
- повтор уже выполненного запроса возвращает сохранённый результат;
- повтор активного запроса возвращает текущий статус;
- явный повторный анализ создаёт новую версию.

Внешний платный вызов нельзя сделать строго exactly-once одной транзакцией Postgres. Если провайдер ответил, а функция умерла до сохранения, повторная оплата возможна. Это остаточный риск, который нужно учитывать в журнале попыток и бюджете.

### 7.5. Ретраи и валидация

Автоматически повторять только ограниченный набор временных ошибок: 429 с учётом `Retry-After`, сетевые сбои, некоторые 5xx. Использовать небольшое число попыток и случайную задержку.

Не повторять автоматически:

- неверный формат файла;
- превышение лимитов;
- отсутствие аудиодорожки;
- неверную авторизацию;
- короткую или пустую запись.

Не допустить умножения ретраев одновременно в SDK, endpoint и браузере.

Zod нужен на границах:

- запрос;
- метаданные загрузки;
- ответ ASR;
- выход AI;
- команда синхронизации;
- импорт.

Помимо типов проверять: длительность, размер, последовательность таймкодов, попадание таймкодов внутрь записи, допустимые ID пунктов каркаса и существование цитат.

## 8. Ревью промпта разбора

Тон, ограничение одним главным замечанием и одним следующим действием подходят продукту. Слабое место — контракт оценки.

| Проблема | Исправление |
|---|---|
| Всегда начинать с вывода, но есть челлендж «Начни с вопроса» | Явно задавать ожидаемый тип начала для конкретного задания |
| «Смотри в объектив» оценивается по транскрипту | Только самооценка; AI возвращает «не могу определить» |
| «На 10% медленнее» без исходного темпа | Нужна сопоставимая базовая запись либо статус «нет базы» |
| Разрыв >0,7 с приравнивается к осознанной паузе | Отделить измеренный интервал от оценки намерения |
| Меньше 20 слов → ясность 1 | Возвращать «недостаточно данных», ясность `null` |
| Паразиты >5/мин всегда главная проблема | Применять только при приемлемом качестве распознавания |
| Только boolean для челленджа | Добавить `unknown` / `not_assessable` |
| Цитаты и время может сочинить модель | Требовать ссылки на индексы слов/сегментов и проверять их |
| `vs_previous` описан строкой «… или null» | Формально определить nullable-поле |
| Нет защиты от инструкций внутри речи | Транскрипт считать данными, не инструкциями |

Дополнительно:

- пункты каркаса должны иметь стабильные ID;
- сохранять версии промпта, модели и входных метрик;
- не отправлять всю историю пользователя: достаточно текущего задания и выбранного предыдущего дубля;
- не перезаписывать ручную коррекцию поздно пришедшим AI-ответом.

Для JSON использовать механизм **Structured Outputs**, затем Zod и смысловые проверки. Указание «только JSON» само по себе слабее формального ограничения ответа. [Anthropic: Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

`claude-sonnet-5-5` — актуальный идентификатор модели. У неё есть особенности управления thinking и параметрами генерации; старые настройки вроде произвольного `temperature: 0` нельзя переносить автоматически. [Anthropic: Sonnet 5.5](https://platform.claude.com/docs/en/models/sonnet-5-5/overview)

## 9. Безопасность, вход и деньги

### 9.1. Доступ только владельцу

Предлагаемый порядок:

1. Заранее создать аккаунт Сергея.
2. Отключить публичную регистрацию и ненужные способы входа.
3. При запросе email-входа использовать `shouldCreateUser: false`.
4. Проверять allowlist email на сервере.
5. После входа проверять стабильный `OWNER_USER_ID`, а не email из тела запроса.
6. Проверять владельца на каждом платном endpoint и разрешении загрузки.

`shouldCreateUser: false` в клиенте не заменяет отключение регистрации на стороне Auth. [Supabase: passwordless sign-in](https://supabase.com/docs/guides/auth/auth-email-passwordless)

Для серверной авторизации проверять JWT установленным SDK; чтение cookie через `getSession()` без проверки недостаточно. SSR-клиенты разделить на браузерный и серверный, обновление cookie выполнять через предусмотренный Next.js proxy. [Supabase: SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs)

### 9.2. Magic link в PWA требует ранней проверки

Письмо может открыть Safari, хотя вход начат из установленной PWA. Нельзя предполагать бесшовный перенос состояния между ними.

Рекомендую проверить оба сценария:

- magic link;
- ввод email-кода непосредственно в приложении.

Для OTP может потребоваться настройка шаблона письма и собственного SMTP. У новых Free-проектов редактирование шаблонов с default SMTP ограничено. [Supabase changelog](https://supabase.com/changelog)

Default SMTP отправляет письма только адресам команды проекта, сейчас ограничен двумя письмами в час и не гарантирует доставку. Для единственного владельца годится для ранней проверки; надёжный повседневный вход требует отдельного решения доставки. [Supabase: SMTP](https://supabase.com/docs/guides/auth/auth-smtp)

### 9.3. Ключи и endpoints

- OpenAI, Anthropic и Supabase secret/service-role — только сервер.
- В браузере допустим Supabase publishable key при корректных правах.
- Не логировать аудио, полный транскрипт, токены авторизации и signed URLs.
- Проверять `Origin` для изменяющих cookie-auth запросов.
- Ограничить redirect URLs входа.
- Не принимать `user_id`, тему и предыдущий дубль на доверии: получать проверенный контекст из БД.
- Рендерить текст модели как текст, без небезопасного HTML.
- Проверять объект Storage до платного вызова: путь, размер, формат, принадлежность.

### 9.4. Rate limit

Для одного владельца достаточно Postgres:

- максимум один активный AI-разбор;
- например, до 6 запусков в минуту;
- до 20 новых разборов в сутки;
- отдельный месячный денежный предел;
- ограничение числа незавершённых загрузок.

Проверка лимита и резервирование попытки должны быть атомарными. In-memory счётчик функции для этого непригоден.

Ограничивать нужно оба платных этапа, даже если endpoint `/api/analyze` исчезнет.

## 10. PWA, офлайн и два устройства

### 10.1. Что работает без сети

После первого успешного открытия:

- тексты упражнений и контент дня;
- тема, каркас, челлендж;
- галочки, дыхание, заметки и ручная самооценка;
- таймер;
- локальная история;
- предварительный XP;
- запись и локальный просмотр при наличии разрешений и места.

Не работают: первый вход, получение чужого устройству свежего прогресса, AI-разбор.

Manifest и иконка не обеспечивают офлайн. Нужны service worker, кэш статических ресурсов, локальные данные и экран восстановления.

Шрифты хранить локально. Для установки на iPhone подготовить подходящие PNG-иконки, включая apple-touch-icon; одним SVG из legacy не ограничиваться.

### 10.2. Очередь изменений

Каждая операция содержит:

- UUID;
- дату сессии;
- исходную серверную revision;
- изменённые поля;
- локальное время;
- идентификатор устройства.

После восстановления сети:

1. обновить авторизацию;
2. получить серверное состояние;
3. применить непротиворечивые изменения;
4. показать конфликты;
5. убрать из очереди только подтверждённые операции.

Запускать синхронизацию при открытии приложения, событии восстановления сети, возвращении на экран и вручную. Не делать Background Sync обязательным условием работы на Safari: API имеет ограниченную поддержку. [MDN: Background Synchronization](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API)

### 10.3. Конфликты

| Изменение | Правило |
|---|---|
| Новые дубли | Объединение по UUID |
| Разные поля одного дня | Автоматическое объединение |
| Один и тот же шаг | При несовместимых правках — конфликт |
| Заметка, самооценка, тема | Не затирать молча; показать локальную и серверную версии |
| Достижения | Объединение, открытие один раз |
| Результат AI | Не заменяет уже внесённую ручную поправку |
| Таймер | Только локально |

Простое объединение `steps_done` через union неправильно: снятая галочка может восстановиться со второго устройства.

Одного `updated_at` для last-write-wins тоже недостаточно: часы устройств могут расходиться. Использовать серверную revision и сравнение изменений с исходным снимком.

Для одного владельца CRDT избыточен. Достаточно контроля версий и трёхстороннего слияния полей.

### 10.4. Ограничения локального хранения

Видео не держать бессрочно в IndexedDB. Предусмотреть сохранение файла пользователем, удаление и понятный срок локального хранения.

Service worker кэширует оболочку и статические ресурсы. Приватные ответы Auth/API и страницы с пользовательскими данными не складывать без разбора в общий HTTP-кэш.

При выходе очищать локальные приватные данные, предварительно предупреждая о несинхронизированных изменениях.

## 11. Импорт legacy

Это миграция формата, а не простая вставка JSON.

### 11.1. Соответствие полей

| Legacy | Новая модель |
|---|---|
| `log[date].f` | Итоговое число паразитов |
| `log[date].r` | Ясность; `0` означает отсутствие оценки |
| `log[date].n` | Заметка |
| `log[date].ch` | Выполнение челленджа |
| `log[date].full` | Исторический факт полного ритуала |
| `log[date].t` | Только час первого сохранения |
| `done[date]` | Выполненные шаги |
| `breath[date]` | Результат дыхания |
| `ach[code]` | Дата открытия достижения |
| `mode` | Режим по умолчанию в профиле |

Создавать сессии по **объединению дат из `log`, `done`, `breath`**. Иначе потеряются частично выполненные дни и дыхательные результаты.

Наличие `log[date]` означает сохранённый день. Наличие только `done` или `breath` — черновой день.

### 11.2. Что восстановить невозможно

Экспорт не содержит:

- выбранную тему;
- точные времена;
- режим каждого исторического дня;
- длительность дубля;
- медиа и транскрипты.

Не выдумывать эти данные. Для задания использовать «неизвестно», при необходимости отдельно показывать вычисленное предположение. `mode` не переносить на все прошлые даты.

`log.t` не превращать в якобы точный timestamp. Для «Ранней пташки» можно сохранить исходный час и признак legacy-происхождения.

### 11.3. Процесс импорта

1. Декодировать base64 как UTF‑8 с поддержкой существующего экспорта.
2. Ограничить размер входа.
3. Проверить структуру, даты, ключи достижений, значения и массивы.
4. Показать предпросмотр: новые дни, совпадения, конфликты, достижения.
5. По умолчанию не перезаписывать существующие итоговые результаты.
6. Применить импорт транзакционно.
7. Зафиксировать хеш импорта для безопасного повтора.
8. Сверить XP, серию и достижения.

В самом legacy импорт объединяет часть данных, но не восстанавливает всё состояние интерфейса и не применяет экспортированный `mode`. Его обработчик не следует копировать буквально.

После перехода нужен экспорт **нового версионируемого формата**. На Supabase Free автоматические резервные копии не включены, поэтому восстановление из экспорта должно быть проверено. [Supabase: тарифы](https://supabase.com/pricing)

## 12. Приоритет исправлений

### P0 — до основной разработки

1. Проверить запись и получение отдельного аудио на реальном iPhone.
2. Перейти на прямую загрузку аудио в приватный Storage.
3. Зафиксировать переход с deprecated ASR до февраля 2027.
4. Разделить черновик и сохранённый день.
5. Ввести единый календарь по таймзоне профиля.
6. Сохранять задание в сессии и дубле.
7. Отключить регистрацию, проверить RLS и доступ только владельца.
8. Определить измеримость челленджей и поправить контракт промпта.

### P1 — до ежедневного использования

1. Идемпотентность, состояния этапов и восстановление после сбоя.
2. IndexedDB, очередь изменений, конфликты двух устройств.
3. Ручная коррекция метрик без потери оригинала.
4. Проверенный импорт и экспорт.
5. Лимиты расходов и журнал usage.
6. Очистка медиа.
7. Проверка email-входа из установленной PWA.
8. Измерение точности паразитов и задержки разбора.

### P2 — после стабильного выпуска

1. Расширенная поддержка файлов из галереи.
2. Forced alignment или более точный акустический анализ.
3. Гарантированная фоновая обработка через workflow.
4. Мгновенные обновления второго устройства через Realtime.
5. Дополнительные графики и длительное хранение медиа.

### Дополнительные несоответствия legacy

- Экспресс скрывает шаги 02 и 05, но оставшиеся подписи дают **11 минут**, хотя режим назван семиминутным.
- Время «Ранней пташки» берётся из `now` при открытии страницы, а не фактического сохранения.
- «Другая тема» может раскрыть тему-сюрприз до старта подготовки.
- Сохранение до последнего шага не даст полный ритуал, пока пользователь не сохранит день повторно.
- Исторические рекорды XP могут изменяться при исправлении старых значений — это следствие текущего пересчёта, а не ошибка синхронизации.

Их следует оформить как отдельные осознанные поправки. Требование «перенести без изменений» не должно скрывать исправление дефектов.

**Лишнее на старте:** универсальный AI framework, отдельный Redis, собственный сервер, микросервисы, сложный event sourcing, обязательный Realtime, полный видеоанализ и FFmpeg WASM.

## 13. Уточнённые четыре этапа разработки

### Этап 1. Проверка рисков и перенос доменной логики

**Работы:**

- ранний HTTPS-деплой на Vercel;
- проверка камеры, микрофона, параллельного аудио и видео на iPhone;
- испытание нескольких реальных MOV;
- сравнительная проверка ASR на размеченных примерах;
- выделение контента, календаря и `calc()`;
- визуальный перенос главной страницы;
- таймер с корректным восстановлением.

**Готовность:**

- основной способ записи работает на iPhone Safari, установленной PWA и Mac;
- 60/90/150 секунд не вызывают падение вкладки;
- известны ограничения импорта галереи;
- XP совпадает с legacy на контрольных историях;
- даты совпадают на устройствах с разными системными часовыми поясами;
- визуал и оба режима проверены на телефоне.

### Этап 2. Данные, вход, синхронизация и миграция

**Работы:**

- таблицы, ограничения, миграции, RLS;
- аккаунт владельца и email-вход;
- разделение черновика/итога;
- IndexedDB и очередь;
- разрешение конфликтов;
- импорт и экспорт;
- базовый офлайн-ритуал.

**Готовность:**

- сторонний пользователь не читает и не изменяет данные;
- два устройства видят один день;
- повтор сохранения не удваивает XP;
- офлайн-изменения переживают перезапуск и синхронизируются;
- конфликт заметки не теряет текст;
- повтор импорта ничего не дублирует;
- экспорт восстанавливается в чистом тестовом окружении.

### Этап 3. Полный AI-сценарий

**Работы:**

- приватная загрузка аудио;
- два этапа обработки;
- транскрипция, метрики, формальная схема feedback;
- карточка разбора и ручная коррекция;
- лимиты, попытки, стоимость;
- очистка файлов.

**Готовность:**

- одинаковый запрос не запускает параллельные платные вызовы;
- сбой feedback не теряет транскрипцию;
- перезагрузка страницы восстанавливает состояние;
- тишина, короткая речь и плохое аудио не получают выдуманные оценки;
- цитаты и таймкоды валидируются;
- AI не оценивает взгляд в объектив по тексту;
- фактическая стоимость и задержки измерены;
- назначен и технически определён переход с Whisper.

### Этап 4. Эксплуатационная проверка

**Работы:**

- завершение PWA-кэширования и обновлений;
- проверка входа, блокировки экрана, смены сети, полуночи;
- проверка удаления данных и восстановления из экспорта;
- проверка бюджетных ограничений;
- несколько последовательных дней реального использования.

**Готовность:**

- семь дней без потери прогресса на двух устройствах;
- офлайн-ритуал доступен после перезапуска;
- интерфейс различает «локально», «синхронизировано», «ошибка»;
- старый service worker не ломает новую версию;
- зависшие задачи и временные файлы очищаются;
- «разбор за ~20 секунд» заменён измеренным ожиданием, включая медленные случаи.
